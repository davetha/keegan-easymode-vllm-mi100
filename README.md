# keegan-easymode-vllm-mi100

Easy-mode Docker Compose launcher for serving **Qwen3.8-27B (INT8)** on **AMD
Instinct MI100** GPUs using [curvedinf/int8-vllm](https://github.com/curvedinf/int8-vllm)
- a vLLM fork with hand-tuned INT8 kernels for MI100 (gfx908).

This repo wraps everything the fork needs into:

- a `docker-compose.yml` that runs the server with the fork's official recipe,
- a `.env` settings file (generated for your machine by `gen-env.sh`),
- a one-shot downloader that fetches the two models (~35 GB) and the INT8 kernel repo,
- this beginner-friendly guide.

## Read this first

1. **"Qwen 27B" here is a specific INT8 build** -
   [Qwen3.8-27B-GPTQ-INT8-W8A8-GS128-PTQR](https://huggingface.co/curvedinf/Qwen3.8-27B-GPTQ-INT8-W8A8-GS128-PTQR)
   (~32 GB) plus a small helper "draft" model
   [Qwen3.8-27B-DFlash2](https://huggingface.co/curvedinf/Qwen3.8-27B-DFlash2-GPTQ-INT8-W8A8-GS128-PTQR)
   (~2.3 GB) that speeds up generation. They are always used together.
2. **The upstream project is validated on 4x MI100.** Running on 2x MI100 works
   memory-wise (this repo sizes the settings for it), but it is *not* a
   configuration the fork author has tested - expect lower speed than their
   published numbers, and be ready to share logs with their issue tracker if
   something fork-specific misbehaves.
3. **One-time cost:** building the Docker images takes 2-5 hours and ~80 GB of
   disk (it compiles PyTorch for MI100). After that, starting the server is one
   command. The first server boot also takes 15-30+ minutes (one-time compile);
   later boots are faster.

## What you need

- Linux host with the AMD GPU driver loaded (`/dev/kfd` exists - run `ls /dev/kfd`)
- Your user in the `video` and `render` groups
- Docker + the compose plugin
- ~250 GB free disk, 64 GB RAM recommended
- Internet access for the builds and model downloads

`gen-env.sh` checks all of this for you and tells you what's missing.

## Quick start

```bash
# 1. Get both repos side by side
cd ~
git clone https://github.com/davetha/keegan-easymode-vllm-mi100.git
git clone --branch main https://github.com/curvedinf/int8-vllm.git
cd keegan-easymode-vllm-mi100

# 2. Generate your .env (checks hardware, does the VRAM math)
bash gen-env.sh

# 3. Build the images (one-time; step A is the slow one, hours)
docker build -f ../int8-vllm/docker/Dockerfile.mi100_base -t aiter-mi100:latest ../int8-vllm
docker compose build

# 4. Download the models (~35 GB, one-time)
docker compose --profile setup run --rm downloader

# 5. Start the server
docker compose up -d vllm
docker compose logs -f vllm        # wait for: running on http://0.0.0.0:8000
```

If `gen-env.sh` can't see your GPUs (unusual driver setups), force it:

```bash
GPU_COUNT=2 VRAM_GIB=32 bash gen-env.sh
```

## Using the server

The server speaks the OpenAI API on the port from your `.env` (default 8000,
localhost only).

```bash
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen3.8-27b-gptq8","messages":[{"role":"user","content":"Hello! What are you?"}]}'
```

- Model name: `qwen3.8-27b-gptq8`
- The model "thinks" first: reasoning arrives in `reasoning_content`, the
  actual answer in `content`. Open WebUI and other OpenAI-compatible clients
  work - point them at `http://<machine>:8000/v1`.
- To open the server to your network: set `PUBLISH_IP` to your LAN IP (or
  `0.0.0.0`) in `.env` **and** add `EXTRA_ARGS=--api-key <long-random-string>`.

Daily commands:

```bash
docker compose up -d vllm     # start
docker compose logs -f vllm   # watch logs
docker compose restart vllm   # after editing .env
docker compose down           # stop (keeps models, kernels, and compile caches)
```

## Settings (`.env`)

Generated by `gen-env.sh`; edit freely.

| Setting | Meaning |
| --- | --- |
| `PORT` / `PUBLISH_IP` | Where the API is reachable. `127.0.0.1` = this machine only. |
| `GPUS` / `TP` | Which GPU indexes to use and the tensor-parallel size (must match GPU count; max 4). |
| `MAX_MODEL_LEN` | Max context (prompt + answer) in tokens. Lower it if startup OOMs. |
| `MAX_NUM_SEQS` | Max simultaneous requests. |
| `GPU_MEM_UTIL` | Fraction of VRAM vLLM may use (0.92 = recipe default). |
| `NS` | Speculative tokens - the speed knob (6 = recipe default). |
| `MODELS_DIR` / `AITER_DIR` / `VLLM_DIR` | Where models, the INT8 kernel repo, and the int8-vllm clone live (relative to this folder). |
| `EXTRA_ARGS` | Extra vLLM flags appended to the serve command (e.g. `--api-key ...`). |

### How `gen-env.sh` picks numbers

It assumes MI100 32 GB cards and the fork's recipe constants: ~31 GB INT8
target weights + ~2.3 GB draft (split across GPUs) + ~2.5 GB per-GPU overhead,
KV cache at ~11.9 KB/token/GPU per TP4 rank (calibrated against the fork's own
published "19 GiB -> 1.6M tokens" figure). It then chooses the largest context
length (65536/32768/16384/8192) that fits your concurrency with 25% headroom.
For 2x MI100 that works out to: ~19 GB used per GPU, ~10 GB left for context
(~450k tokens of cache), 32768 context, 6 concurrent requests.

## Troubleshooting

- **Startup OOM** -> lower `MAX_MODEL_LEN` to 16384 and/or `MAX_NUM_SEQS` to 3.
- **`permission denied /dev/kfd`** -> missing `video`/`render` group or missing
  `--device` flags (the compose file already passes them).
- **Crash mentioning TP/parallel/rank** -> that's the untested-2-GPU territory;
  try rerunning with `VLLM_G128_GLUON=0` added under `environment:` in
  `docker-compose.yml`, and keep the log for the upstream issue tracker.
- **GPUs on PCIe, no XGMI link** -> runs, but some fast paths stay off
  (`gen-env.sh` reports this; `rocm-smi --showtopo` shows the topology).
- **Base image build OOMs** -> rerun step 3A with `--build-arg MAX_JOBS=8`.
- **Port already in use** -> `gen-env.sh` auto-picks a free one, or set `PORT`.
